## (B) Blocking issues (must-fix before implementation)

### B1 — Upgrade-over-install is asserted (FR-5) but never tested

**Evidence.** `01` FR-5: "installing a newer version over an older one replaces the app cleanly." `02` WP3 matrix item 8 tests only **"Re-install over uninstall"** — that exercises a clean directory, not an occupied one. Since v1.0.0 is the first release there is no older version to upgrade from, but an **occupied-install overlay** (installer run while a previous copy is installed, app closed) is testable and is the closest proxy for NSIS's real upgrade path (same GUID, file replacement, shortcut re-registration). NSIS one-click installers can also fail silently on locked files if the app is *running* — neither doc mentions this at all.

**Fix.** Add to the WP3 matrix (and M1 criterion 2):
- Item 9: with the app installed and **closed**, re-run the same installer → installs cleanly over `%LOCALAPPDATA%\Programs\Interviewer`, shortcuts survive, app launches, Apps & Features shows one entry (not two).
- Add to `docs/INSTALLATION.md` FAQ and release-notes template §4/known-issues: **"Close Interviewer before installing a newer version"** (locked-file behavior of NSIS one-click).

### B2 — asar completeness gate ignores non-TS assets (the `prompts.json` startup dependency)

**Evidence.** `src/services/PromptManager.ts:1` does `import promptsRaw from '../data/prompts.json';` and `src/electron_app/main.ts:14` imports `PromptManager` — so a missing `prompts.json` in the asar is a **hard startup crash**, not a feature gap. Neither document's M0/WP1 asar-listing criterion checks non-TS assets; both reason only about `node_modules` dependencies. Neither doc even mentions `prompts.json`.

**Good news (verified empirically, §D row 21):** TypeScript **does emit imported JSON** to `outDir` — proven with the repo's own tsc 5.9.3 in two scratch builds replicating the exact repo pattern (JSON pulled in via a non-`include`d imported file). So `dist/electron/src/data/prompts.json` is produced by CI's `npm run build` and is covered by the existing `files` glob `dist/electron/**/*`. The local `dist` copy is semantically IDENTICAL to `src/data/prompts.json` (byte-size difference is 2-vs-4-space indentation only). The config is sufficient — but only by luck of the default glob, and no gate would catch a regression.

**Fix.** M0 criterion 2 / WP1 DoD evidence must additionally show `npx asar list` output proving: (a) `dist/electron/src/data/prompts.json` present; (b) prod deps `axios`, `openai`, `pdf-parse`, `mammoth`, `uuid` present; (c) `electron-store`, `react*`, `zustand`, `lucide-react`, `clsx`, `tailwind-merge`, `date-fns`, `form-data` absent.

### B3 — "Apply §4.2 verbatim" would break package.json

**Evidence.** Stage 1 §4.2 is **annotated JSONC** (`// FROZEN FOREVER`, `// 🚩G: build/ is gitignored`, …) — comments are invalid in `package.json` and would break `npm ci` immediately. It also **omits existing fields** `mac`, `linux`, and `forceCodeSigning` (`package.json` L101–107); a literal replacement would silently delete them. Stage 2 says "Apply Stage-1 §4.2 verbatim unless this plan overrides" (`02` WP1) and flags the no-comments issue only for freeze *markers* (`02` M0.5), not for the block as a whole.

**Fix.** Stage 4 must **merge** the new keys into the existing `build` object using the exact, valid JSON given in **§E.2**. No comments anywhere in `package.json`; freeze markers live in `02` decision log D6 and the WP4 workflow header comment.

### B4 — `SHA256SUMS.txt` is specified for generation but never uploaded

**Evidence.** Stage 1 §4.3 Bug-A fix sets upload paths to exactly `release/*.exe`, `release/latest.yml`, `release/*.blockmap`. Stage 2 WP4 item 1 repeats these three paths; item 3 adds checksum generation; item 7/M2-b/SM-4/D10 all require `SHA256SUMS.txt` in the release. **No step adds the checksum file to the `upload-artifact` paths**, so the release job (which re-uploads only the downloaded `windows-build` artifact) would publish a 3-artifact release, failing the program's own frozen artifact-set definition on the first tagged run.

**Fix.** Upload paths in the rewritten `build-windows` job are exactly: `release/*.exe`, `release/latest.yml`, `release/*.blockmap`, `release/SHA256SUMS.txt`. (Checksum file is written into `release/` before upload.)

## (C) Non-blocking recommendations

- **N1 — Remove the vestigial dispatch input.** `electron-release.yml` L13–17 defines a **required** `version` input for `workflow_dispatch`. Post-rewrite, dispatch is smoke-only (no release), so this input is meaningless friction. Remove it (or make optional with description "unused — releases are tag-driven"). Neither doc mentions it.
- **N2 — README has two more false statements WP5 must fix.** L35 claims "**Cross-Platform Desktop App** … for Windows, macOS, and Linux" while v1 ships a Windows-only installer; L148 says "React 18" while `package.json` L38 has `react ^19.2.4`. Both contradict the docs' own "no contradictions" DoD — add to WP5 scope.
- **N3 — Version-guard placement.** Put the tag↔version guard **immediately after checkout, before `npm ci`** — the negative test (M2-c) then fails in seconds instead of after a full dependency install.
- **N4 — Icon source is non-square.** `public/logo.png` is **187×185** (verified via PNG IHDR), so the Stage-2 interim "upscale to 256×256" must **pad to square first** (transparent/white) or the mark distorts. Multi-size `.ico` must include 256×256, 128, 64, 48, 32, 16.
- **N5 — INSTALLATION.md FAQ additions:** (a) close-app-before-upgrade (B1); (b) non-ASCII usernames and long paths are safe (electron-builder ships Unicode NSIS; install path `%LOCALAPPDATA%\Programs\Interviewer` is shallow); (c) per-user install needs no admin rights and writes nothing outside `%LOCALAPPDATA%`/`%APPDATA%`.
- **N6 — Environment-B smoke data safety.** The installed app and the dev checkout share `%APPDATA%\ai-interviewer` (verified expectation, §D row 23). Back up that folder before the dev-account functional smoke so dev data isn't mutated by the packaged build.
- **N7 — Record installed footprint at WP3** (Apps & Features size) so release-notes "disk guidance" is a measured number, not a guess.
- **N8 — Favorable quirk worth noting in the workflow comment:** the existing tag glob `v*.*.*` (`electron-release.yml` L11) also matches prerelease tags like `v1.0.0-rc.1` — required for the dry run; keep it.
- **N9 — `uuid` v13 is `"type": "module"`**: the compiled CJS `require("uuid")` resolves via the `node` condition export (`dist-node/index.js`) and works because Electron 40's Node supports `require(esm)` (verified: `require('uuid')` succeeds in the repo's Node; local packaged app ran per commit 0449dfb's fix history). **`uuid` must stay in `dependencies`** — it is main-process runtime. Persona creation in the WP3 smoke covers it.
- **N10 — Stage-2 "docs/ SCREAMING_SNAKE_CASE convention" claim is shaky** (`docs/github-templates/bug_report.md` is lowercase). `INSTALLATION.md` is fine either way; don't spend time on it.
- **N11 — pdf-parse v2.4.5 is dual-format** (`require` → `.cjs` fallback exists) — the dynamic `import('pdf-parse')` asar edge case is real but mitigated; the WP3 .pdf/.docx matrix item is the right gate. `mammoth` is plain CJS.
